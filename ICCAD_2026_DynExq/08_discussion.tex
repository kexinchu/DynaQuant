\section{Limitations and Scope}
\label{sec:limitations}

\paragraph{Host capacity and startup.}
\systemname\ keeps kernel-ready higher- and lower-precision expert representations in host memory. This removes online repacking from the critical path but increases pinned-DRAM demand and may be unsuitable for memory-limited edge hosts. Disk-backed representations would reduce steady host use at the cost of another latency tier. Dual-tier packing and pinned-cache construction are currently untimed startup costs; a production service would need to persist or amortize them.

\paragraph{Scheduling objective.}
The policy optimizes aggregate routing utility. It provides neither per-tenant quality guarantees nor fairness when concurrent requests come from different domains, and per-request precision choices would make batching less regular. Tenant weights or service-level constraints could extend the selection objective without changing the underlying replacement protocol.

\paragraph{Platform and model generality.}
The evaluation covers one 48\,GB GPU and three model families. Transfer overlap, kernel availability, and feasible higher-precision capacity vary with accelerator architecture, interconnect, sequence length, and KV-cache policy, so the reported operating points are not universal constants. The pinned MoE-Infinity runtime supports only the Qwen3-30B checkpoint in our model set and differs from the implementation described in its paper; the executable offloading comparison is therefore limited to that model. \systemname\ also assumes two precomputed tiers and does not yet coordinate capacity across GPUs. Finally, a fixed task order controls history within each comparison but does not test robustness to workload permutations. Cross-task averages are descriptive because task sizes and metrics differ; statistical tests remain paired and per task.

\paragraph{Kernel maturity.}
The prototype favors inspectability over peak kernel performance. Qwen-family dispatch uses eager expert execution because the upstream grouped-GEMM path does not accept per-expert versioned handles. A fused handle-aware grouped kernel is needed to determine how much of the remaining overhead is fundamental rather than implementation-specific.

\paragraph{Memory and synchronization boundary.}
The hard invariant covers \systemname-owned expert pools, staging blocks, and declared conversion workspaces. Whole-process HBM safety remains conditional on the serving configuration respecting startup reservations for the KV cache, activations, and framework allocations; \systemname\ does not replace the framework allocator. A separate CUDA stream removes explicit migration synchronization from the forward path but cannot eliminate shared-bandwidth contention. Reported latency covers isolated model execution and excludes queueing, tokenization, network transport, and serialization.
