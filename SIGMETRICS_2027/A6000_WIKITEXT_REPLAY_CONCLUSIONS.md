# A6000 × WikiText 第一轮结论与优化分析

日期：2026-10-03。对应计划 `IMPLEMENTATION_EVALUATION_PLAN.md` 的 P0：共用决策栈、一个数据集、一张 A6000。

## 1. 这轮实际跑的是什么

两张 RTX A6000 都被其他用户占满（`jis23009` 的 futurekv，合计约 70GB、利用率 100%），`/home/kec23008/Models/` 里也没有可加载的 MoE checkpoint。按计划里的计时纪律，在共享 GPU 上新测端到端延迟会被判无效。因此这一轮没有假装跑了 kernel 计时。

跑的是 **deadline replay**。输入全部来自已经在 A6000 上测过、并登记在仓库里的工件：

| 输入 | 来源 | 数值 |
|---|---|---|
| 数据集 | `results/paper/qwen30b_routing_active_set_trace.json` | WikiText-103，不相交 2048-token 块；主结果用 2048，128 和 512 是同一条 trace 的短前缀 |
| 模型 | Qwen3-30B-A3B，48 层，每层 128 专家 | 每点 2 个 warmup trial、10 个 measured trial |
| 低/高块 | `qwen30b_dynaexq_bs1.json` 的 pool | 2,506,752 B / 9,437,184 B，高块是低块的 3.76 倍 |
| 已部署预算 | 同上，`pool_allocation_bytes / 48` | 619,659,264 B/层，Φ = B / P_lo = **1.931** |
| 带宽 | `qwen30b_offload_waiting.json` 的 H2D 拷贝 | 2048 token 点上 **24.86 GB/s** |
| 2048 的层窗口 | 同一次运行的 TTFT 均值 / 48 | **38.58 ms**，这是实测 |
| 128 / 512 的层窗口 | 按 token 数从 38.58 ms 线性缩放 | 2.41 ms / 9.64 ms，**这是假设，不是新测量** |
| 质量 | `results/perplexity/Qwen3-30B/30b-*.txt` | WikiText-2，全高精度参考 7.191 |

预注册的两个质量界都保留了，没有事后改：ΔPPL ≤ 0.5（计划）和 ΔPPL ≤ 2.1（背景图里已经用过的界）。静态策略只在 warmup trial 上选配置；`oracle-grid-test` 在 measured trial 上选，单独标出。

代码在 `dynaexq/lease/`（账本、单流 deadline replay、交换）和 `dynaexq/policy/online.py`。不变量测试 `dynaexq/tests/test_lease_invariants.py`，11 项通过。原始结果在 `results/paper/a6000_wikitext_replay/summary.json`。在线策略每层预算都没有越界（`within_budget: true`）。

Replay 不是端到端 TPOT。它回答的是计划里的 Go/No-Go：在这份 A6000 测量上，联合分配有没有一个内点，以及在线交换有没有打过静态联合配置。

## 2. 结论

### 2.1 已部署的 29.7GB 预算上，2048-token prefill 没有联合分配问题

Φ = 1.931、ΔPPL ≤ 2.1 时，每层 30 个高精度专家（ΔPPL = 2.094）之后还剩 98 个低精度驻留位，128 个专家全能留下。precision-only、horizon-only、seq-pq、seq-qp、static-joint、oracle、两种 DynaByte 的 exposed wait 都是 **0**。DynaByte 在这个点上接纳了 0 笔交换。

这不是实现失败。质量下限和全量驻留同时放得下，lookahead 没有可争夺的字节。计划里的边界政策在这里是对的：联合协调器应该退化，而且它退化了。

### 2.2 ΔPPL ≤ 0.5 在这张 A6000 上不可行

高精度块是低精度块的 3.76 倍。要碰到 ΔPPL ≤ 0.5，曲线要求大约 70% 的专家是高精度，字节需求约 2.63 × P_lo，大于已部署的 1.931 × P_lo。把预算全部给 fidelity，最多约 65 个高精度专家，插值后的 ΔPPL 是 **+1.005**，此时低精度驻留只剩约 2 个，exposed wait **199 ms**。

所以计划里预注册的 0.5 不能当这张卡的主约束。主约束应该放在测量能达到的区域。ΔPPL ≤ 2.1 刚好在 30/128 个高精度专家处成立（7.191 + 2.094 = 9.285，界是 9.291）。

### 2.3 联合分配有一个真实的内点，但它不在长 prefill 上

质量可行的区域从 Φ ≈ 1.0 开始（Φ = 0.70 和 0.85 连 30 个高精度专家都放不下，静态联合配置全部 infeasible）。

在 **实测的 2048-token、38.58 ms 窗口**上，Φ = 1.0 和 1.3 的校准最优都是 0 个 staging slot。精度一旦满足，剩下的字节全部给驻留。lookahead 不在内点上。

把层窗口缩到短上下文之后，内点出现了。Φ = 1.3、ΔPPL ≤ 2.1：

| 策略 | 128 token（窗口 2.41 ms，缩放） | 512 token（窗口 9.64 ms，缩放） | 2048 token（窗口 38.58 ms，实测） |
|---|---:|---:|---:|
| precision-only，0 slot | 54.3 ms | 83.7 ms | 125.3 ms |
| seq-qp，先锁住 slot 再补精度 | 54.3 ms | 83.7 ms | 125.3 ms |
| static-joint / seq-pq | **24.1 ms**（16 slot） | **77.6 ms**（8 slot） | 125.3 ms（0 slot） |
| oracle-grid-test | **12.6 ms**（16 slot） | **54.1 ms**（16 slot） | **105.4 ms**（4 slot） |

128 token 上，同样满足 ΔPPL ≤ 2.1，把 16 个驻留位换成 lookahead，平均 exposed wait 从 54.3 ms 降到 24.1 ms。seq-qp 拿不到这个点：它在「还没有高精度专家、低精度池放得下」时把 slot 锁成 0，补上精度、挤掉驻留之后也不重新打开 lookahead。这是本轮最清楚的负面对照，也是计划里要求的强组合基线，不是稻草人。

2048 的校准网格没选出 slot，但测试集 oracle 要 4 个 slot，125.3 ms 降到 105.4 ms。校准静态配置在长 prefill 上低估了 lookahead。

### 2.4 在线交换没有打过静态联合配置

2048 token、Φ = 1.3、ΔPPL ≤ 2.1，这是在线策略唯一有等待可降的实测点：

| 策略 | 平均 exposed | p95 | 交换 |
|---|---:|---:|---:|
| static-joint-cal | 125.35 ms | 138.14 ms | 校准一次，之后冻结 |
| dynabyte-counterfactual | 121.13 ms | 133.81 ms | 114 笔，全部由 donor 出资，113 笔命中后转成驻留 |
| dynabyte-independent | 117.82 ms | 129.77 ms | 318 笔，4 笔过期 |
| oracle-grid-test | 105.41 ms | 121.41 ms | 测试集上选的格子 |

在线反事实策略比静态联合好约 4 ms，离 oracle 还差 16 ms。10 个 trial 的 p95 区间互相盖住，不能写成稳定优势。独立估值接纳了大约三倍的交换，端到端只快 3 ms，同样盖不住。单元测试里，反事实对「预取一个已经驻留的专家」给 0 分、独立估值给正分；这个差异在这条 trace 上没有变成可见的尾延迟损失。

计划里的判定可以直接用：

- **J1（内点）部分成立。** 短窗口、Φ = 1.3、ΔPPL ≤ 2.1 时，最优点是 30 个高精度 + 37 个低精度驻留 + 16 个 slot，不在坐标轴上。长 prefill 的实测窗口上，最优点退回「精度下限 + 其余全部驻留」。
- **J2（在线打过充分调优的静态联合）不成立。** 在线与 static-joint 同档。该收缩的是在线控制，不是联合配置本身。
- **J3（独立估值在端到端上有害）不成立。** 机制差异在单测里成立，在这条 trace 上没有变成等待时间差异。
- **J4（逐专家 q_i）这轮没有测。** 质量用的是已测的整模型 perplexity 曲线，不是在线风险账。

## 3. 优化分析

字节该给谁，由窗口能不能盖住 miss 决定，不由一个固定比例决定。

一个低精度专家的传输时间是 2.51 MB / 24.86 GB/s ≈ **0.101 ms**。38.58 ms 的层窗口理论上能盖住约 380 个低精度专家，所以 2048-token prefill 里，只要驻留集合已经挡住大部分活跃集，再预留 slot 没有校准收益。2.41 ms 的窗口只能盖住约 24 个专家，而 Φ = 1.3 在拿出 30 个高精度专家之后，低精度驻留不够挡住短 prompt 的活跃集，slot 就变成 2 倍差异。

由此得到四条实现上的优先级，按对下一轮实测的影响排：

1. **把实验主区间改到「刚能满足质量」的预算，而不是已部署的 Φ = 1.93。** 在 1.93 上，任何策略的等待都是 0，表格会看起来没有方法差异。Φ = 1.0 是 ΔPPL ≤ 2.1 的可行性边界，等待约 180–300 ms，但 slot 已经挤不进去（30 个高精度 + 15 个低精度就把预算用完）。Φ = 1.3 是两者都还有余量的点，本轮唯一同时看到质量可行和 lookahead 收益的地方。
2. **下一轮真实计时优先测短窗口，不要再加长 prefill。** 用户之后补的其他 GPU，建议同时给这张 A6000 补 128 和 512 token 的实测 TTFT，以及 decode 的逐 token 路由。本轮 128/512 的窗口是按 token 线性缩放的，只能用来发现内点，不能写进论文表格。Decode 的活跃集更小、窗口更短，是联合分配更可能成立的区域；现在的 trace 只有整段 prefill 的唯一专家集合，没有逐 token 路由。
3. **seq-qp 这种「先把 lookahead 锁死」的顺序要留在论文里当主对照。** 它和 static-joint 共用同一个预算、同一套 replay，差别只是 slot 在看到精度成本之前就冻结。128 token、Φ = 1.3 上是 54.3 ms 对 24.1 ms。固定 50/30/20 切分更差，但它是因为 30% 的字节买不够 30 个高精度专家，ΔPPL 停在 2.20–2.56，质量约束直接失败。质量失败的点不能拿来比速度。
4. **在线控制器下一刀不要加更复杂的估值，先把 horizon 和预测集对准 oracle 已经指出的 slot。** 2048、Φ = 1.3 上，校准静态选了 0 个 slot，测试 oracle 要 4 个，在线反事实只收回了 4 ms 里的一小部分，而且 114 笔交换几乎全部命中后转成驻留。说明频率先验看得太满（warmup 的平均活跃集宽度是 105 个专家），donor 经常是另一个很快会被用到的专家，反事实因此拒绝大部分交换。独立估值不拒绝，所以交换数变成 318，但等待几乎不变。下一步是把预测集收到「下一层真正多出来的专家」，而不是整层频率 top-105；horizon 保持 1 在短窗口上不够，oracle 用的是最多提前一层、但一次发出 16 个 slot。

## 4. 对论文主张的直接影响

可以写的：在 A6000 实测字节、带宽和 WikiText-2 曲线下，ΔPPL ≤ 2.1 需要约 23% 的专家保持高精度；这份精度会把 Φ = 1.3 的低精度驻留从 128 个打到 53 个以下。短计算窗口里，把一部分驻留改成 lookahead，比「先定精度、slot 固定为 0」少一半以上的 exposed wait。已部署预算（Φ = 1.93）和 ΔPPL ≤ 0.5 分别是退化点和不可行点。

先不要写的：在线 byte-exchange 优于充分调优的静态联合配置；独立估值在端到端上造成重复计价损失；ΔPPL ≤ 0.5 可在这张 48GB 卡上达到。这三条都被这轮数据拒绝或尚未测量。
